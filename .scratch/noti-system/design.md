# สเปก: ระบบแจ้งเตือนงานต่ออายุ / งาน MA

Status: draft v6 — grilling รอบ 1–2 ยืนยันครบ (ดูตาราง "การตัดสินใจที่ยืนยันแล้ว") — เหลือ frontier สุดท้าย 3 คำถาม (overdue, วันที่รอบถัดไป, คอลัมน์ระบบ) แล้วเริ่มสร้างได้

## ที่มา

ทีมติดตามงานต่ออายุสัญญา/ใบรับรอง (SSL, โดเมน, ลิขสิทธิ์ซอฟต์แวร์ ฯลฯ) ของหน่วยงานภาครัฐหลายแห่ง ผ่าน Google Sheet ที่แชร์กันระหว่างทีม ปัจจุบันไม่มีอะไรเตือนเมื่อใกล้หมดอายุ ทำให้งานต่ออายุหลุดได้ เป้าหมายคือระบบที่แจ้งเตือนผู้เกี่ยวข้องเมื่อรายการใกล้ครบกำหนด พร้อม web app สำหรับจัดการข้อมูล (ผู้รับ, การจัดฝ่าย, รอบเตือน)

## ภาพรวมระบบ (4 ส่วน)

1. **ข้อมูลงาน** — Google Sheet (ผู้ใช้กำลังไล่ใส่ข้อมูล)
2. **ตัวตรวจ + แจ้งเตือน** — รันทุกวันเช้า (เวลาไทย): อ่านชีต → คำนวณ → ส่งผ่าน 3 ช่องทาง
3. **Supabase** — เก็บข้อมูลการจัดการ (ผู้รับ, การจัดฝ่าย, รอบเตือน, log) + Auth
4. **Web app บน Vercel** — หน้าจัดการข้อมูลแบบ login + API route ที่ cron เรียก

## ข้อมูลต้นทาง (สถานะ ต.ค. 2026)

- Google Sheet 1 ไฟล์ — Sheet ID เก็บผ่าน env/secret เท่านั้น (repo เป็น public)
- 4 แท็บ แบ่งตาม sales เจ้าของงาน (1 คนต่อ 1 แท็บ)
- โครงสร้างแต่ละแท็บ:
  - แถว 2: ชื่อ section (ปัจจุบันมี "งานต่ออายุ") — อนาคตอาจเพิ่ม section "งาน MA"
  - แถว 3: หัวคอลัมน์ — Job Code, ชื่องาน, หน่วยงาน, ประเภทการต่ออายุ, วันหมดอายุ, ต่ออายุครั้งที่1, กำหนดต่ออายุ, ต่ออายุครั้งที่2, partner, ผู้ติดต่อ (+ สถานะการต่ออายุ 4 ช่อง ที่จะเพิ่มมา)
  - แถว 4+: ข้อมูล โดย 1 Job Code อาจกินหลายแถว (หนึ่ง job มีหลายรายการย่อย เช่น หลายโดเมน/หลาย SSL)
- ตำแหน่งคอลัมน์เพี้ยนระหว่างแท็บ → parser ต้อง map จากชื่อหัวคอลัมน์ ห้าม hardcode ตำแหน่ง
- ข้อมูลกำลังถูกไล่ใส่เพิ่มเรื่อยๆ — ระบบต้องทนต่อแท็บที่ยังว่าง/ข้อมูลไม่ครบ

## ปัญหาข้อมูลที่ต้องออกแบบรับมือ (สำคัญสุด)

คอลัมน์ "วันหมดอายุ" ทั้งหมดเป็นข้อความอิสระ หลายรูปแบบปนกัน:

- `"28 สิงหาคม 2568 - 27 สิงหาคม 2569"` (ไทย พ.ศ., เป็นช่วง)
- `"08 December 2026"` (อังกฤษ)
- `"24/04/2026 - 23/04/2027"`, `"Period : 02/12/2025 - 01/12/2026"` (อยู่ในคอลัมน์กำหนดต่ออายุ)
- มี typo ในข้อมูลจริง เช่น ช่วงวันที่ปีเดียวกันทั้งสองฝั่ง

แนวทางรับมือ:

1. ตัวระบบ parse เอง — รองรับไทย พ.ศ. / อังกฤษ / dd/mm/yyyy, ช่วงวันใช้**วันสิ้นสุด**เป็นตัวตั้งต้นการนับเตือน
2. รายการที่ parse ไม่ได้ ส่งไปแจ้งเจ้าของแท็บในหมวด "ข้อมูลมีปัญหา" ให้ไปแก้ชีต
3. (แนะนำ) เพิ่มคอลัมน์ระบบ "วันหมดอายุ (ระบบ)" ในชีต — ระบบเขียนค่าที่ parse แล้วกลับลงไป ตรวจสอบด้วยตาได้

## สถาปัตยกรรม

- **Stack เดียวทั้งระบบ: Next.js (TypeScript)** deploy บน Vercel, ฐานข้อมูล + Auth บน Supabase
- **ตัวตรวจ-แจ้งเตือน = API route** (`/api/cron/daily-check`) ที่ Vercel Cron เรียกทุกวันเช้า ป้องกันด้วย `CRON_SECRET` — domain logic อยู่ใน `lib/` ที่ทั้ง API route และหน้าเว็บเรียกใช้ร่วมกันได้
- ทางเลือกสำรองถ้า cron ของ Vercel ไม่ตรงเวลาพอ: GitHub Actions ยิง endpoint เดียวกัน (repo พร้อมอยู่แล้ว)
- ทุกการติดต่อภายนอกอยู่ชั้นขอบ: Sheets API, SMTP, Discord webhook, Telegram API

### ช่องทางแจ้งเตือน — 3 ช่องทางพร้อมกัน

ผู้ส่งเป็น interface เดียว มี 3 implementation (digest ชุดเดียวกัน เรนเดอร์ตามช่องทาง):

| ช่องทาง | วิธีส่ง | ต้นทุน | หมายเหตุ |
|---|---|---|---|
| Email | Email API (ผู้ให้บริการรอยืนยัน — ต้องเป็นเจ้าที่ยืนยัน sender โดยไม่บังคับโดเมน เพราะใช้อีเมลใหม่ที่เพิ่งสมัคร) | ฟรี (Brevo 300/วัน ยืนยันแล้วจากหน้า pricing) | เรนเดอร์เป็น HTML ตารางสวย |
| Discord | Incoming Webhook | ฟรี ไม่จำกัด | เรนเดอร์เป็น embed, ตั้งง่ายสุด |
| Telegram | Bot token + chat_id | ฟรี ไม่จำกัด | เรนเดอร์เป็นข้อความ markdown |

- ต่อคนเลือกได้ 1+ ช่องทาง — จัดการผ่านหน้าเว็บ
- เพิ่มช่องทางใหม่ภายหลังได้โดย implement interface เดิม

## โครงสร้างโค้ด (ออกแบบเพื่อรองรับการอัปเดตในอนาคต)

หลักการ 4 ข้อ:

1. **แกน logic บริสุทธิ์** — `lib/domain/` ไม่รู้จัก Sheet/DB/API ใดๆ รับ-ส่งเป็นโครงสร้างข้อมูลล้วน ทดสอบได้โดยไม่ต้องมีเน็ต
2. **Adapter อยู่ขอบ** — ทุกการติดต่อภายนอกอยู่ชั้นขอบต่างหาก
3. **Config อยู่ในฐานข้อมูล** — สิ่งที่ทีมปรับเองได้ (ผู้รับ, ช่องทาง, รอบเตือน) แก้ผ่าน web app ไม่ต้อง deploy ใหม่
4. **ไม่สร้างสิ่งที่ยังไม่มีข้อมูล** — สงวนช่องไว้ให้งาน MA แต่ไม่เขียน parser MA จนเห็นข้อมูลจริง

### จุดขยาย — การอัปเดตแต่ละแบบกระทบอะไร

| การอัปเดตในอนาคต | ต้องแตะ | ไม่ต้องแตะ |
|---|---|---|

| เพิ่มช่องทาง (Teams/Slack/…) | เพิ่ม 1 ไฟล์ใน lib/notifiers/ + dropdown ในหน้า recipients | แกน logic ทั้งหมด |

| รูปแบบคอลัมน์สถานะเปลี่ยน | row-reader + renewal-rounds เท่านั้น | notifiers, หน้าเว็บ |
| ปรับรอบเตือน | แก้ในหน้า /settings (ไม่ deploy) | โค้ด |
| เปลี่ยนตัวรัน (Vercel cron → GH Actions/เครื่องเรา) | เรียก endpoint เดิมจากที่ใหม่ | ทั้งหมด |
| ข้อมูลไหลเข้าเรื่อยๆ ในชีต | ไม่ต้องแตะ — อ่าน dynamic ทุกรอบรัน | — |

### ขอบเขตต่อชิ้น (สำหรับเขียนเมื่อสั่งสร้าง)

- `SectionParser.parse(rows) → JobItem[]` — ต่อ section type (ต่ออายุ / MA ในอนาคต)
- `DateParser.parse(text) → date | ParseError` — error ที่อ่านได้ ไปโผล่ในหมวด "ข้อมูลมีปัญหา"
- `DueRules.dueDates(item, role) → Date[]` — ฝ่ายต่างกัน รอบต่างกัน จากตาราง settings
- `RecipientResolver.resolve(tab) → {sales, productBuddy, quoting}` พร้อมช่องทางต่อคน
- `Notifier.send(recipient, digest)` + `Renderer.render(digest, channel) → Message`
- `RenewalRounds.currentRound(item) → {n, done}` — state machine ครั้งที่ 1–4

| `channels` | id, person_id → people, type (email\|discord\|telegram), contact, active | ช่องทางต่อคน (1 คนมีได้หลายช่อง) |
| `assignments` | id, sheet_tab, sales_id, product_buddy_id, quoting_id | ผูกแท็บในชีต → ผู้รับ 3 ฝ่าย (หน้า /assignments) |
| `settings` | id (1 แถว), lead_times (jsonb ต่อฝ่าย), send_time, timezone | รอบเตือน 30/14/7/3/1, 60/45/30, เวลาส่ง |
| `notify_log` | id, sent_at, person_id, channel, item_count, details (jsonb) | ประวัติการแจ้งเตือน — ตรวจย้อนหลังได้ |

- Contact จริง (อีเมล, Discord webhook URL, Telegram chat_id) อยู่ในตาราง `channels` — **ไม่มีอะไรลง repo**
- ทุกวันที่ cron รัน จะเขียน `notify_log` → Supabase free tier ไม่หลับ (pause เมื่อไม่มี activity 1 สัปดาห์)

## Web app — หน้าจอและสิทธิ์

- **Login**: Supabase Auth — แนะนำ magic link (ไม่ต้องจำรหัสผ่าน) หรือ email+password ตามสะดวก
- **Allowlist**: ล็อกอินได้เฉพาะอีเมลของทีม (รายชื่ออยู่ในตาราง allowed emails / หรือ admin เพิ่มให้) — คนนอกแตะไม่ได้
- **RLS (Row Level Security)**: ทุกตารางต้อง login ก่อน ถึงอ่าน/เขียนได้ — ทีมเล็ก ให้สิทธิ์ระดับ "ล็อกอินแล้ว = แก้ได้ทุกอย่าง" พอ (ยังไม่ต้องทำ role ซับซ้อน)
- หน้าจอทั้งหมด: `/login`, `/recipients`, `/assignments`, `/settings`, `/history`

## ตรรกะการแจ้งเตือน

- สำหรับแต่ละรายการ คำนวณ "จำนวนวันคงเหลือ" จากวันหมดอายุ (ใช้วันสิ้นสุดของช่วง ถ้าเป็นช่วง)
- แต่ละฝ่าย: รวบรวมรายการที่วันนี้ตรงกับรอบเตือนของฝ่ายนั้น → ส่ง 1 ข้อความ/ฝ่าย/วัน
- เนื้อหา: หัวข้อ "งานใกล้หมดอายุ X รายการ (วันที่ ...)" + รายการ (Job Code, ชื่องาน, ประเภท, วันหมดอายุ, เหลือกี่วัน, partner, ผู้ติดต่อ) + หมวด "ข้อมูลมีปัญหา" ถ้ามี
- **รอบการต่ออายุ (state machine)**: แต่ละรายการมีรอบปัจจุบัน (ครั้งที่ 1–4)
  - เมื่อสถานะการต่ออายุของรอบปัจจุบันถูกทำเครื่องหมายว่าดำเนินการแล้ว → หยุดแจ้งรอบนั้น
  - นับรอบถัดไปจากวันหมดอายุชุดใหม่ (จาก "กำหนดต่ออายุ" หรือวันหมดอายุที่อัปเดต)
  - รูปแบบค่าจริงในคอลัมน์ "สถานะการต่ออายุ" ยังไม่ทราบ — parser ตั้ง tolerant และรอเห็นของจริงก่อน
- แยกหมวดในข้อความ: "ใกล้หมดอายุ" / "เลยกำหนดแล้ว" (บอกว่าเลยมาแล้วกี่วัน) / "ข้อมูลมีปัญหา" (parse ไม่ได้ / ไม่มีวันหมดอายุ / ต่อแล้วแต่ไม่มีวันหมดอายุชุดใหม่)
- รัน-ส่ง 08:00 Asia/Bangkok ทุกวัน (DRY_RUN เปิดอยู่ = คำนวณ+เขียน notify_log อย่างเดียว ไม่ส่ง)

## ขอบเขตเวอร์ชันแรก (ไม่ทำ)

- ไม่แก้ข้อมูลที่ user กรอกในชีต (เขียนกลับได้แค่คอลัมน์ระบบ ถ้าตกลงทำ)
- ไม่ทำระบบ role/สิทธิ์ซับซ้อนใน web app (ล็อกอิน = แก้ได้)
- ไม่ทำส่วน "งาน MA" จนกว่าจะมีตัวอย่างข้อมูล MA ในชีต

## คำถามค้างที่ต้องยืนยัน

1. รายชื่ออีเมลทีมสำหรับ allowlist login + contact ของผู้รับแต่ละคน (อีเมล / Discord webhook / Telegram chat_id) — ใส่ผ่านหน้าเว็บภายหลัง
2. งาน MA + ข้อมูลเพิ่มเติมทั้งหมด — ผู้ใช้กำลังไล่ใส่ข้อมูล รอแล้วอัปเดตสเปกอีกรอบ

## ข้อจำกัดของ free tier (รู้ไว้ก่อนใช้)

- **Supabase free**: โปรเจกต์หลับ (pause) ถ้าไม่มี activity 1 สัปดาห์ — ระบบนี้เขียน log ทุกวันจึงไม่มีปัญหา, DB 500 MB เกินพอ
- **Vercel Hobby (free)**: cron ได้ 1 ครั้ง/วัน ตรงกับความต้องการอยู่แล้ว, เวลารันเป็นช่วงกว้าง ~1 ชั่วโมง (ไม่เป็นไรเพราะแจ้งเตือนเป็นรายวันอยู่แล้ว)

## ข้อกำหนดความปลอดภัย (repo เป็น public)

- ห้าม commit ข้อมูลลูกค้า/หน่วยงาน/partner/อีเมลจริงลง repo
- Env บน Vercel เท่านั้น: SUPABASE_URL, SUPABASE_ANON_KEY, **SUPABASE_SERVICE_ROLE_KEY** (ใช้เฉพาะ server/cron), GOOGLE_SHEET_ID, GOOGLE_SERVICE_ACCOUNT (JSON), EMAIL_API_KEY, CRON_SECRET
- `/api/cron/*` ต้องมี CRON_SECRET ทุกตัว — คนนอกยิง endpoint ไม่ได้
- RLS ทุกตาราง + allowlist login
- ชีตแชร์เป็น "anyone with link" อยู่แล้ว — พิจารณาลดสิทธิ์เหลือเฉพาะคนในทีม + service account
